## 决策 1：删除 D02/D03，只承诺单片段能力

- **问题**：早期 12 维设计里，D02「因果信号」与 D03「角色弧光」需要读完整个长文本才能判断，单片段环境无法产出，只好留 postprocess 脚本事后补。
- **否决**：补全 postprocess + 状态机——工作量翻倍且超出 Skill 可靠能力边界；或允许两维先 null 后处理——污染下游聚合。
- **方案**：删除两维，本 Skill 只承诺单片段能力；跨片段关系由独立的二阶段跨段分析承担（见决策 14 的 Layer 4）。
- **收益**：立刻可运行、无空函数占位；诚实边界——不承诺做不到的事。

## 决策 2：统一键名，Schema 与校验器对齐

- **问题**：输出键名曾混用中文别名与编号 ID，校验器按一套写、示例按另一套写 → 校验 100% 报错，等于没校验。
- **方案**：输出 JSON 只用 `D01/D04/D05/D06/D07/D08/D09/D10/D11...` 编号键名；`references/schema.md` 说明文字可留中文，但机器相关字段（校验器维度集合、SKILL.md 速览）与 JSON 键名严格一致。
- **收益**：任何产物 100% 可通过校验器；下游解析器无需处理别名。

## 决策 3：Hash 标准化而非逐字匹配

- **问题**：对原文逐字符 sha256，用户做合理清洁（末尾空行、Windows 换行 `\r\n`、尾随空格）后 hash 全变 → 同文本重复标注意外失败。
- **否决**：模糊 hash（simhash）引入依赖与误报。
- **方案**：`strip()` + 统一换行为 `\n` 后 sha256 取 16 位；标准化算法在 schema.md 定义且各处实现一致。
- **收益**：格式调整不再破坏 hash；仍是零依赖强确定性的 SHA256。

## 决策 4：Skill 本体与脚本解耦

- **问题**：早期把脚本写进核心工作流，暗示 AI 会自动执行（自动切分、循环读 JSONL、写回）。实际 Skill 生态 = System Prompt 注入，AI 只在对话里输出内容，不执行 Python 文件循环。
- **否决**：把脚本逻辑写进 Prompt（不可控）；放弃脚本全手动（易错）。
- **方案**：SKILL.md 只承诺「给一段文本 → 输出批注 JSON」；scripts/ 是可选辅助工具；批量调度由调用方管线代码承担。
- **收益**：Skill 在任何平台可用（含纯手动）；脚本零依赖可随时手动跑。

## 决策 5：Pass 分层——客观 → 结构 → 阐释

- **问题**：一次性全维判断时，主题（高主观）会反向污染叙事功能（低主观）——AI 在想主题时把背景铺垫误判成转折。
- **方案**：客观事实 → 结构位置 → 阐释判断严格分层执行；最主观的一层默认不启用，用户明确要求时才跑。
- **收益**：维度间污染显著下降、token 与幻觉双降；天然对应三档分级。

## 决策 6：多义性承载——主值 + alternatives

- **问题**：AI 常在歧义维度上反复涂改，耗时且丢掉其他合理解释。
- **方案**：主值只取最相信的一个；其余合理解释全部写进 `alternatives`（layer/dimension/value/reason）；禁止在主值上反复纠结。
- **收益**：提速；下游可把 alternatives 当软标签做置信度加权训练。

## 决策 7：锚点分层——内联摘要 + 文件按需查阅

- **问题**：全部锚点/示例/枚举塞进 SKILL.md 后超过 700 行，AI 读到后段对前面定义已模糊，错误率上升。
- **否决**：全内联（烧 token + 注意力稀释）；完全不内联（90% 场景也要检索）。
- **方案**：SKILL.md 内联关键摘要（够 90% 场景）；边界犹豫时再精确查阅 `references/*-anchors.md` 完整分档。

## 决策 8：脚本零第三方依赖

- **问题**：精确 token 计数要引 200MB 的 tokenizer 依赖，为一个切分脚本不值。
- **方案**：token 用「中文 1 字 ≈ 1、英文 1 词 ≈ 1」近似；全部脚本只用 Python 标准库。将来需要重依赖时放 `scripts/optional/`，不影响核心脚本零依赖。

## 决策 9：三档分级不写三份 Skill

- **问题**：按档级写三份 SKILL.md，升级要同步三份，必然版本漂移。
- **否决**：加命令行参数（Skill 机制不支持参数）；写三份（维护 ×3）。
- **方案**：一份 Skill，按用户意图 + `annotation_pass`（P1 轻量 / P1+P2 标准 / P1+P2+P3 深度）自然区分档级。
- **收益**：下游按 `_metadata.annotation_pass` 筛选即可划分数据集档级。

## 决策 10：脱敏导出机制打包进 Skill

- **问题**：版权合规要求入库前剥离原文。若脱敏脚本在包外，容易被后人遗忘，含原文数据直接入库。
- **方案**：export_dataset.py 内置 `scripts/`，带「原文键名黑名单」递归清理——即使误填 `raw_text`/`原文片段` 等字段也会被自动替换为 `【已脱敏】`。
- **收益**：脱敏是使用流程的一部分，「忘记做合规」的概率从架构上被压低。

## 决策 11：速览表枚举内联

- **问题**：速览表只写维度说明、枚举值藏在 schema.md，实测 AI 不主动翻 references，直接自造非枚举值。
- **否决**：schema 全量内联（被决策 7 否过）；只加「见 schema.md」提示（AI 仍不翻）。
- **方案**：速览表内联全部**硬约束枚举值**（写值必须严格选）。锚点类校准参考（强度分档等）仍留 references。
- **收益**：首次批注即写对，去掉「先错 → 翻文档 → 改」循环。

## 决策 12：输出落盘与 skill 包隔离

- **问题**：实测 AI 把批注结果写进 `examples/`。Skill 要打包分发，运行时产物写进包内会污染分发包、带走别人的批注数据。
- **方案**：SKILL.md 定义「输出落盘约定」：纯 LLM 手动保存；Agentic 写 `<调用方工作区>/outputs/annotations/<doc_id>/`；并设红线——**运行时产物禁止写入 `examples/` 或包内任何目录**。
- **收益**：分发包纯净；多文档产物以 `<doc_id>` 目录聚合并隔离。

## 决策 13：（v2.5 已废弃）可选上传模块

历史决定曾允许「可选上传批注数据用于训练收集」，v2.3 周期内默认关闭。v2.5 起按架构设计移除（见决策 14）。本条目仅作历史追溯。

## 决策 14：v2.5 架构升级

- **背景**：对 v2.3/2.4 的联合评审发现规格方向正确，但实现有 7 项 P0 bug；评审结论是「架构不需要继续迭代规格，需要修 bug、跑真实全本验证」。
- **方案（落地清单）**：
  1. 3 层单 JSONL → **四层分离**：L1 结构 / L2 阐释 / L3 文笔每层独立 JSONL + L4 跨段**二阶段**（全书一次，不混在逐段批注里）+ Phase 4 merged 嵌套文档；
  2. 7 项 P0 修复：segment_id 全局计数（防碰撞）、切分坐标自校验断言（漂移即抛异常）、无章节边界退化切分（**永不截断**）、frontmatter 显式输出、Layer 4 从「恒空占位」改为启发式规则可运行、merge 读对 text_span 字段、segment_id 统一带 doc_id 前缀；
  3. **移除上传模块**：Skill 不内置网络调用，保持「纯 Prompt 包 + 本地工具」的纯粹定位；数据收集如需恢复由独立模块承担，不改回本 Skill；
  4. **schema 单一真源**：枚举此前在 SKILL.md / 校验器 / 模板三处手抄对不齐 → 全部以 `references/schema.md` 为准，改枚举先改它再同步下游；
  5. 恢复 checkpoint 状态机（原子写 / status / reset-layer / reset-all）。
- **否决**：craft span 用全局偏移——frontmatter 修订会导致已完成的 span 全部漂移，必须「段内相对偏移 + merge 时换算」；Layer 4 在逐片段里顺手做——局部视图看不到伏笔-回收。
- **验证**：在真实全本（公版长篇）上跑通——章节边界命中、逐段坐标自校验全过、5 份模板 0 error 通过校验器。
- **代价**：v2.3 单 JSONL 产物与新结构不兼容，需迁移或重跑。

## 决策 15：v2.6 升级——全本运行补丁 + D04.polarity

> ⚠️ 本决策中 D04.polarity「可选」方案已被发布前复核推翻，同日由决策 16 改为必填。

- **背景**：真实全本运行暴露：① Windows GBK 控制台打印 emoji 崩溃；② annotate_segment 的 `--checkpoint` 目录未真正用于读取（路径错位 → 重复标记判断失灵）；③ Phase 3 完成不写 `cross_segment_completed`。另有体验缺口：Markdown 报告缺 L2/L3 摘要、HTML 报告缺 D04 极性列。
- **方案**：
  1. 全脚本 stdout/stderr 强制 UTF-8（Windows 安全）；
  2. checkpoint 全面支持 `base_dir`/`--dir`，Phase 3–5 各写各的完成标记；
  3. D04 新增 `polarity`（positive/negative/neutral/mixed），校验器版本集放宽（当时定可选，决策 16 改必填）；
  4. cross_segment 规则条目标记 `_source:"rule"`，重跑默认 `--preserve-curated` 保留人工/LLM 核验条目；
  5. MD 报告补 L2/L3 摘要、HTML 报告加极性列；
  6. 新增 `scripts/fill_spans.py`：对存量产物缺失/漂移的 span 一次性回补（定位失败不写、报告人工处置）。
- **否决**：cross_segment 补 stage_started 字段（非必需、schema 噪音）；外部质量评分进 Schema（评分是评测管线职责，不是分析产物字段）。

## 决策 16：D04.polarity 从「可选」改为「必填」

- **背景**：本 Skill 调用方式没有运行期选择点——不存在让用户决定「这轮填不填 polarity」的开关。无选择点的固定流程里，可选字段 = 同批产物字段形态不稳定，下游统计被迫处理分叉。
- **否决**：维持可选（字段分叉）；删除 polarity（需求已确认）；只提示不校验（模型系统性偷懒省略）。
- **方案**：v2.6.0+ 产物 `D04.polarity` 必填、四值枚举校验；拿不准时按「core → 极性」缺省映射兜底写 `neutral`/`mixed`，不存在必须省略的情形；**2.5.0 旧产物版本分支豁免**（零迁移）。
- **收益**：同流程产物字段同构，模型无退路，下游极性统计零分叉。

## 决策 17：D19 情感分析层（v2.7，P4 Pass + 独立 emotion.jsonl）

- **背景**：D19 曾因范围控制被暂缓，并留下恢复前置条件：分段坐标自洽、segment_id 唯一连续、场景边界不引入 scene_id、实体链接不内置、D04 与 D19 职责边界明确。v2.6.0 交付后逐条核查达标，正式恢复为 v2.7。
- **否决**：D19 回写 interpretation.jsonl 既有行——违反层文件 append-only 语义 → 独立产物文件 `{doc_id}_emotion.jsonl`；引入 `scene_id` 全库重切分——成本高且破坏既有坐标 → arc/target/trigger 允许 null；内置指代消解/实体映射表——属下游聚合职责 → `target.entity_id` 允许 null、name 用段内实指。
- **方案**：
  1. schema_version / skill_version 升 2.7.0（宽松兼容：仅新增可选字段 + 新产物文件，L1–L3 schema 不变，2.5/2.6 旧产物零迁移）；
  2. D19 是**阐释层语义扩展，不是独立架构层**；产物落独立 `emotion.jsonl`（P4 独立调用/独立校验/append-only），merge_layers 并入 `merged.emotion`；
  3. D19 字段：`primary`（emotion/intensity/polarity）/ `secondary`（复合，可 null）/ `target` / `trigger` / `arc`（段内情感弧，可 null）/ `expression`（direct/indirect/key_phrases/note）；`emotion` 枚举真源为 `references/emotion-lexicon.md`（Plutchik 8 基元 + 中文文学扩展 = 44 词）；`key_phrases` 必须逐条通过原文子串校验；
  4. P4 触发条件（任一命中才跑，否则登记 `emotion_skipped`）：`D04.intensity ≥ 4`；`D01 ∈ {激励事件, 上升行动, 高潮, 转折}`；`D10` 非 null（含对话）；用户显式要求；
  5. checkpoint 增加 `emotion` 层名与 `emotion_skipped` 数组（与「没批」区分）；annotate_segment 支持 `--layers emotion`（自动注入该段 D01/D04/D10 作触发上下文 + 从 segments 补齐 text_span 供子串校验）。
- **收益**：复合情感、情感对象、触发点、段内情感弧成为一等产出，为跨段「角色情感轨迹」聚合提供数据底座；P4 可独立重跑不污染 L1–L3；旧产物零迁移。
- **代价**：每个触发段新增一次 P4 调用（≈ L2 单层成本）；情感词表需随语料维护。

### 决策 17 备忘与已知边界

- **边界 ①（冲突优先级）**：同一段 D04（段级氛围）与 D19（角色级情感）都产出判断时**以 D19 为准**；跨段「角色情感轨迹」聚合（实体归并/双轨保留）属下游模块职责，Skill 内不实现。
- **边界 ②（词表演化）**：44 词为起始规模；协议：同语义出现 ≥3 次自动入表、近义词合并、总量控制 50–80；触达 50 时复核入表阈值与校验器白名单逐词同步流程（这是 Schema「枚举唯一真源」规则的唯一特例）。
- **边界 ③（触发条件 4 无结构位）**：P4 触发条件「用户显式要求」在产物结构里无字段记录——由使用方在调用 `--layers emotion` 时自行行使；判定不触发时仍登记 `emotion_skipped`。

## 决策 18：工程化修复轮——补齐 Agent 自动化执行缺口（v2.7 修复轮，未升版）

- **背景**：多次真实运行（月亮与六便士全本 98 段、上海堡垒试用、v2.7 D19 demo）反复暴露一个共性：`annotate_segment.py` 的设计假设是「人在终端里操作——打印 prompt → 人复制给 LLM → 粘贴 JSON 回去」，但实际执行者是**有代码能力的 Agent**。Agent 每次都要自写胶水脚本（`_gen_*.py` / `_commit_*.py` / `find_span()`）补全「生成→校验→落盘」链路；实测一次全流程**只用 2/9 个脚本**，核心调度壳完全被绕过。
- **问题清单（两方诊断收敛）**：
  1. 无 `--input-json`：脚本没有「直接喂入已生成 JSON」的可重入口；手动模式虽读 stdin，但每个 layer 各读一次，多层时第二次即 EOF 退出，且无法静默调用；
  2. 文档声称的「校验失败自动重试 3 次」在代码中**不存在**（检索 0 命中），校验失败直接退出码 3；
  3. 无批量驱动：一次调用只批一个 `(segment, layer)`，一本书只能手工循环；
  4. span 生成期无自动定位：craft 条目要 LLM 手工数段内偏移（`fill_spans.py` 已有回算能力，但被定位成「2.5.0 存量迁移工具」，未接入生成/校验主流程）——这是 LLM 高频失误点，也是 Agent 自写 `find_span()` 的直接原因；
  5. 分级策略只管「层」不管「段」：没有「哪些段跑深度档/轻量档/跳过」的采样规则，实际执行靠人工选段 → **被动抽样**（开头 7 段 + 结尾 7 段、中间 61 段跳过）；
  6. 「纯 Prompt 包 / scripts 可选」定位表述误导——对纯 LLM 手动降级模式成立，但对完整工作流（切分/校验/合并/报告）scripts 是骨架；
  7. SKILL.md 34.9KB 过重，Agent 每次启动认知负荷高。
- **方案（落地清单）**：
  1. `annotate_segment.py` 新增 `--input-json <file>`：接受单对象或 JSONL 多行（每行含 segment_id + layers），自动匹配待批 (segment, layer)，静默走「校验→落盘→checkpoint」；手动 / `--llm-cmd` 路径保留；
  2. 校验失败自动重试 ≤3 次：将 fill_spans 的定位算法抽成公共模块 `scripts/span_locator.py`；annotate_segment 校验失败时若属 span/引文定位类错误 → 自动回算修正后重试——兑现文档长期声称的「自动重试 3 次」；
  3. 批量驱动并入 annotate_segment：新增 `--all-pending`（遍历 checkpoint 未完成的 (segment, layer)），批内单条失败记 failed 清单后继续，不整批退出；
  4. 新增 `scripts/select_segments.py`：读 structure.jsonl 的 D01/D04 判定 → 输出「深度档/轻量档/跳过」段清单——让「20% 深度档提供 80% 价值」从人工拍脑袋变规则驱动，与「先全量轻量 structure、再按需深度层」的分层架构天然配合；
  5. 新增 `scripts/run_pipeline.py`：Phase 1–5 一体化薄编排壳，`--resume` 读 checkpoint 跳过已完成；Phase 2 段批注不捆绑 API（沿用 `--llm-cmd` / `--input-json` 注入 / 纯规则骨架三种模式）；
  6. SKILL.md 定位改写：明确「纯 LLM 手动模式可用；完整工作流以 scripts/ 为核心组件」，消除「可选辅助」误导；新增 `RUNBOOK.md`（Agent 最小操作契约：CLI 速查 + 校验错误快速修复表 + 常用流程）；
  7. SKILL.md 瘦身：Layer 速览/枚举/锚点压成 references 指针，正文只留工作流 + 硬约束 + 关键摘要（34.9KB → 目标 ~18KB 内，须保住纯手动模式可独立使用）。
- **否决**：新起第 10 个 `batch_annotate.py`（驱动并入 annotate_segment，避免脚本碎片化）；validate_output.py 内置修复逻辑（校验器保持纯校验单一职责，修复在调度壳层做）；本轮升 v2.8.0（无 schema 变更——四者一致原则下 schema 版本不应空转，本修复轮保持 v2.7.0，合入下个 feature 版本时再吞并）。
- **验证**：沙箱端到端最小样例——preprocess → annotate `--input-json`（含**故意错 span**条目验证自动修复重试）→ select_segments → run_pipeline `--resume` 续跑 → validate 全绿 → merge/report。
- **收益**：Agent 跑全流程无需自写任何胶水；「不全量精读」从被动妥协变为显式档位选择（成本纪律可执行化）。
- **代价**：CLI 参数面增大（文档需跟上，RUNBOOK 兜底）；run_pipeline 是薄壳，依赖各 Phase 脚本接口稳定。
